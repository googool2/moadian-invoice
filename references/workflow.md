# Workflow: keys, certificate, serial, sending, inquiry

Read this when the user wants to actually send an invoice, set up keys, or understands the taxid.
Only `scripts/send_invoice.py` signs and sends. It uses moadian-full's `Moadian` client and
sends **only after the user explicitly confirms**, through a two-step `prepare` → `send --confirm`
flow (§5).

Sources: S3 = RC_DCPS.SN_V1.3 (official); L = moadian-full 0.0.2 source; T1 = official Java SDK
mirror github.com/SoftwareNasr/ir.gov.tax.tpis.sdk `TaxUtils.java`; T2 = official .NET SDK
mirrors (SoftwareNasr/tax.collect.data.sdk `TaxIdGenerator.cs`, 0.0.27 `TaxIdProvider.cs` in
mojtabahakimian/Taxation); T3 = github.com/ali-hallaji/digi-tax-ops (real accepted taxids and
sandbox experiments); errors.md E-ids for API errors. All T* are secondary copies of SDK code.

## 1. Security rules (not negotiable)

- The private key and certificate are read **only from a file path or an environment variable**
  (e.g. `MOADIAN_PRIVATE_KEY_PATH`, `MOADIAN_CERT_PATH`). Never paste them into chat, never write
  them into the repository, examples, config files or logs. If a user pastes a key into the chat,
  do not repeat it, do not store it, and tell them to rotate it (generate a new key pair and
  re-register the public key in کارپوشه) because it has now left their machine.
- Keep keys outside the project folder, with file permission 600; add `*.pem`, `*.key` to `.gitignore`.
- Nothing is sent to tp.tax.gov.ir without an explicit "yes, send" from the user **after** they
  have seen the validated invoice (taxid, buyer, totals) and the target environment.
- This skill is not tax advice: it checks format and arithmetic against INTA documents, not
  whether a transaction is taxable or which rate/type is legally right.

## 2. What the taxpayer needs (summary of L's API; registration steps are outside this skill)

| item | where it comes from | used by |
|---|---|---|
| memory id «شناسه یکتای حافظه مالیاتی» (6 chars) | کارپوشه › عضویت › شناسه‌های یکتای حافظه مالیاتی | taxid, `fiscalId`, token `clientId` |
| private key (PEM, RSA) | generated by the taxpayer; its public key is registered for the memory id | signing token and invoice (L `encryption.sign`, RS256 JWS) |
| certificate (PEM, `-----BEGIN CERTIFICATE-----`) | issued for that key; a CSR does **not** work (errors.md §6) | `x5c` header of the JWS |
| seller economic code (tins) | taxpayer registration | header.tins |

API flow in L (`main.py`, base URL `https://tp.tax.gov.ir/requestsmanager/api/v2/`):
`GET nonce` → token = JWS of `{nonce, clientId}` → `GET server-information` (tax system public
key) → invoice JSON signed (JWS) then encrypted (JWE RSA-OAEP-256 / A256GCM) → `POST invoice` →
`GET inquiry-by-uid` / `inquiry-by-reference-id`. Status values: SUCCESS, FAILED, IN_PROGRESS,
NOT_FOUND; TIMEOUT means **not registered** (errors.md §4).

Send-path defects in L. `send_invoice.py` fixes these at run time without modifying the
installed library:

| defect in L | effect | fix in `send_invoice.py` |
|---|---|---|
| `encryption.py` sets the JWS `sigT` once, at import | a long-running process signs with a stale time [effect on the server UNVERIFIED] | sets `sigT` to the current time on every signature |
| `_get_tax_gov_key` caches the server public key forever in the system temp dir (`tax_gov_key`) | key rotation is never picked up, and sandbox and live share one cached key | fetches `server-information` once per run, in memory only |
| URLs are hard-coded to live in `settings.py` | no way to target a sandbox | URLs are rebuilt from the chosen target's base URL |
| `load_pem_private_key(password=None)` | password-protected keys are rejected | decrypts with `MOADIAN_PRIVATE_KEY_PASSWORD` in memory; nothing is written |
| HTTP errors are re-raised as a plain `Exception` | callers cannot tell what happened | reported as JSON with a reminder to run `inquiry` before any resend |

Base URLs:
- **Live:** `https://tp.tax.gov.ir/requestsmanager/api/v2/` (RC_TICS.IS v1.6).
- **Sandbox:** not in the official spec or the SDK samples (the SDK takes any base URL).
  T3 used host `sandboxrc.tax.gov.ir`, but the full API path is [UNVERIFIED]. The user must set
  `MOADIAN_SANDBOX_BASE_URL` from their trusted company / INTA.

## 3. taxid and inno (S3, T1, T2)

Structure (S3 Table 1): `MEMORY_ID(6) + hex(days since 1970-01-01, 5) + hex(serial, 10) + check(1)`,
22 characters, upper case.

Check digit (S3 §3-1-4 and Appendix 1; identical in T1 and T2):

```
control = toDecimal(MEMORY_ID) + pad(days, 6) + pad(serial, 12)     # decimal, zero-padded
toDecimal: digit -> itself, letter -> its code point ("A" -> "65")
check   = Verhoeff(control)
```

S3 Appendix 1: `DEF5GH`, day 18463 (1399/04/30), serial 12 → control
`68697057172018463000000000012` → check 2 → `DEF5GH0481F000000000C2`. moadian-full 0.0.2 returns
`…C7` for the same input (it maps letters base-36 over the hex string, and its Verhoeff generator
uses the validation permutation). Two real accepted taxids from T3 (`A41XRD050B1006A5E4C549`,
`A2HP31050B0006A607FE94`) also verify only with the official algorithm. Use `scripts/taxid.py`.

- days are counted in UTC (T1/T2 divide epoch seconds by 86400; S3 itself names no time zone
  [UNVERIFIED]). An invoice at 01:00 Tehran time belongs to the previous UTC day.
- Uppercase the memory id before converting (T1 converts before uppercasing; lower case gives a
  different digit).
- Memory id alphabet (S3 p.6): 1-9 and A D E F G H K M N O P R T W X Y Z; 0, I, J, L, Q, V
  forbidden; B, C, S, U reserved.
- **inno = taxid[11:21]** (the 10-hex serial). Official SDK samples do this; a sandbox test (T3)
  got warning 1300501 with a decimal inno and none with the hex serial. S1 §7-5 says inno is a
  10-char hexadecimal serial; that it must equal the taxid serial is from T2/T3 [secondary].

## 4. Serials

- Never reuse a taxid: a resent taxid is rejected with 0300101 and does not overwrite the stored
  invoice (errors.md). After a FAILED status, fix the invoice and send it with a **new serial**.
- moadian-full's `SerialManager` builds serials from `unix_time × 100 + random(10..99)` and keeps
  the last 1000 in `serial_history_<memory id>.json` in its storage folder (default: current
  directory). `build_invoice.py` points it at `~/.moadian-invoice/` so the project stays clean.
  Two machines sending for the same memory id can still collide; give each a separate serial range.
- S1 §7-5 asks for ascending serials; time-based serials satisfy that within one process.

## 5. Sending — two steps

1. `python scripts/send_invoice.py prepare invoice.json --target sandbox|live`. This step is
   offline and needs no key. It:
   - runs the validator with the current time;
   - blocks invoices more than one week old (S1 §7-2; the validator alone only warns);
   - blocks a taxid that already has a receipt;
   - prints a summary and a confirmation code (a hash of the exact JSON, target and base URL).
2. Show the user the type/pattern/subject, buyer, line count, tbill, taxid and target, and get an
   explicit yes for this invoice.
3. `python scripts/send_invoice.py send invoice.json --target … --confirm <code>`. This step:
   - re-checks everything and refuses if the code does not match;
   - reads the key and certificate from the environment variables only, and refuses a key that
     sits inside a git repository;
   - for live, also needs `MOADIAN_ALLOW_LIVE=1`, set by the user.

   The receipt (uid, referenceNumber, response; no secrets) is written to
   `~/.moadian-invoice/receipts/<taxid>.json`.
4. Processing is asynchronous: `send_invoice.py inquiry --target … --uid <uid>`. On FAILED run
   `scripts/explain_error.py --from-response`. After a network error during `send`, run `inquiry`
   first: the invoice may already be registered, and a resent taxid is rejected (0300101).

`send_invoice.py fiscal-info --target …` is a read-only connection test for the memory id.
